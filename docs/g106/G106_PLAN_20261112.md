## 3. Plan for (2): Options alerts concentrated on NVDA

**Why it happens** (live data, Nov 12 to 16:37 UTC): O1 ("High Volume/OI Participation") selects a streamed contract
when its day volume is at least 3x prior-day OI and the print rules pass. Evaluations / SELECTED by name: NVDA 4,322 /
504, QQQ 246 / 4, AAPL 381 / 0, AMZN 217 / 0, NFLX 99 / 0, SPY 88 / 0, TSLA 67 / 0, MSFT 15 / 0, IWM 8 / 0. NVDA's
watched contracts traded 3-3.5x their OI (160 C 13,986 vs 4,520; 155 P 33,940 vs 9,807); the near-the-money contracts
of SPY/QQQ/AAPL carry large OI and rarely reach 3x. Two design gaps make it one-name:

1. **No per-name cap is enforced.** The flow policy declares 3 candidates per underlyer, 20 per session and per-profile
   budgets (`ADVANCED_OPTIONS_FLOW_POLICY.md`, "Candidate Caps And Deduplication"), but notes they are policy
   metadata with no enforcement; in code only the O3 input builder has a per-underlying bound
   (`advanced_options_o3_inputs.py`). O1's only output limit is 20 per run (`FlowStrategyPolicy.maximum_candidates`).
2. **O1 sees 72 contracts, not the chain.** The breadth layer already finds volume/OI >= 3 contracts on every name
   (the Unusual-activity screens: prior OI >= 500, Vol/OI >= 3, tier minimums, 3 per name, 20 total), but those are
   screen observations, not alerts, because tradable alerts need print evidence (aggression side), which only the
   streamed contracts have.

**Plan** (each behind its own switch, default off; replay before live):

| Step | Change | Effect | When |
|---|---|---|---|
| O1D.1 | Enforce the declared caps on new O1 alerts: at most 3 new alerts per underlying per run, ranked by the policy's order (complete evidence, aggression confidence, premium, cluster, vol/OI, freshness); repeat hits on an existing alert are not capped (R46 keeps one row per contract and side) | Stops one name filling the list; does not invent signals for names that do not qualify | Build Nov 12-13 night; replay Nov 10-12 evidence (counts per name before/after); live the next session with the user's go |
| O1D.2 | Show the breadth Unusual-activity rows as **observations** beside the alerts (Options Alerts page, own section; 3 per name, 20 total, ranked by day premium), clearly not tradable | Every name's unusual contracts are visible each window | Frontend + API read, Nov 13-14 |
| O1D.3 | V4 depth (section 2) chooses streamed contracts by breadth activity, so active contracts on more names get print evidence and can become O1 alerts | Real diversity of tradable alerts | With V4 |
| O1D.4 | Tier-relative thresholds for O1 (ETF / core mega-cap / high-beta minimums like the screens) instead of one 3x rule | Better balance across products | Research first (Nov 9-12 outcomes per tier), then a versioned policy |

## V4.1 implementation note (Nov 12 night; code after the r99 rehearsal, not in r99)

Where the profile is chosen: the Options lifecycle's preparation takes `admission_profile_version` (one of
`c6_activity_momentum_v1/v2/v3`; live runs v2) and loads `realtime/policies/advanced_options_activity_momentum_c6_<v>.json`
through `load_activity_momentum_profile`. V3-only behaviour (expiry calendars, same-day, near/end-of-week targets) is keyed
on `version == SUCCESSOR_ACTIVITY_MOMENTUM_PROFILE_VERSION` in `advanced_options_automatic_preparation.py` (~1119) and
`scripts/prepare_advanced_options_v3_pre_session.py` (~130, 277, 930, 944, 952). Changes:

1. `advanced_options_activity_momentum_c6.py`: `V4_ACTIVITY_MOMENTUM_PROFILE_VERSION = "c6_activity_momentum_v4"`, its
   path, status `C6_V4_DEPTH_RUNTIME_LOADED`, root keys = v3's + `product_buckets`; a `_V3_FAMILY` set (v3, v4) replacing
   the `== SUCCESSOR` checks above (v3 behaviour unchanged).
2. Validation for v4: 24 contracts per underlying (default = maximum), budget 216 of 900 at 9 names; v2/v3's fixed 8/12/4/4
   checks stay for v2/v3 only.
3. `product_buckets`: product recognised from the listed expirations at preparation (an underlying with expirations on at
   least 4 of the next 5 sessions = DAILY_EXPIRY, else WEEKLY_EXPIRY). DAILY_EXPIRY: SAME_DAY 0 DTE 6, NEAR 1-2 DTE 6, WEEKLY
   (the next weekly expiries) 8, CORE 6-21 DTE 4. WEEKLY_EXPIRY: WEEKLY 8 (includes the 0 DTE contracts on the stock's own
   expiry day), CORE 6-21 DTE 12, EXTENSION 22-60 DTE 4. Calls and puts ranked together by one quality score (quote present,
   prior OI, nearness to the delta anchor, previous-session volume and notional, spread); complete groups only, 12 per role.
4. Downstream checks: slot set and ingress plan at 216 (< 1,000 quote ceiling), `maximum_contracts_per_logical_shard`,
   market-state shard map (one shard), the window's per-contract reads; no 3-4 DTE contract in the O1 lanes (flow boundary).
5. Tests: profile load and identity; allocation on the recorded Nov 12 catalog/quote capture offline (per-name counts per
   bucket, roles, groups, product recognition for SPY/QQQ/IWM vs the stocks; NFLX's thin chain); v2/v3 allocations unchanged.
