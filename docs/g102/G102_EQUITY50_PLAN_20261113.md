## 1. What a ticker needs before it can join (from the code, not estimates)

Per ticker, the portal history plan (`realtime/equity_portal_history.build_realtime_equity_portal_history_plan`, session
Nov 12) expects 13,804 bars from 5 provider requests:

| Interval / basis | Bars | Depth |
|---|---|---|
| 1d ADJUSTED | 283 | 2025-09-30 .. last session |
| 1wk ADJUSTED | 261 | 5 years |
| 1mo ADJUSTED | 60 | 5 years |
| 1d RAW_UNADJUSTED | 90 | raw window (90 sessions) |
| 5m / 15m / 30m / 1h RAW | 7,020 / 2,340 / 1,170 / 630 | 90 sessions |
| 1m RAW | 1,950 | 5 sessions |

25 new tickers: 125 provider requests, 345,100 bars (50 in total: 250 requests, 690,200 bars). REST is unlimited (user,
Nov 12), so the backfill itself is minutes, not hours.

Besides bars, the R40 readiness check (`runner/ticker_readiness.py`) requires per ticker: reference fields, split and
dividend coverage, earnings coverage through the session close (stocks), fundamental reports (stocks), the previous
session's RTH intraday completeness, 1h depth of 20 sessions, and a ticker workspace without missing producers.
Signals that read history: O1/O3 30m trend (202 completed 30m bars = 16 sessions) and the 21-day liquidity, OS1/OS2
history; all within the 90-session raw window.

- Equity window run time doubles in the per-ticker stages; measured on the copy first (step 5). If over budget, the
  ticker workspace and screening stages are the first candidates for sharding.
- Stock Alerts and the screener read the universe; a universe change is a new revision for them (saved state per
  rule version is unaffected, new tickers start empty).
- Names with a split inside the 90-session raw window get their 30m/1h setups withheld until the split ages out (TP6).
- Fundamentals: ETFs have none by design (`BY_DESIGN` in the readiness check).
