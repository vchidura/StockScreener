**V2/V3 review, 2026-10-30: retain the core data architecture, repair runtime recovery, and separate qualification from daily operation.**

The current Advanced implementation is a substantial pipeline with useful correctness guarantees. It is not yet a proven unattended daily service. Moving it from Docker to host Python will simplify debugging but will not remove its authorization, history, readiness, or recovery constraints. The recommended sequence is local deterministic replay, a bounded live segment using the same runtime, Docker replay, then a full live Docker session and a multi-session soak.

This review covers the current working tree, including existing uncommitted changes; the named design documents; Advanced acquisition, journals, bindings, scheduler, canonical alerts, deployment and qualification code; and selected tests. It excludes review or modification of the separate legacy Developer application. The Advanced implementation's explicit dependency on retained Developer historical data is included because it affects V3 startup. No runtime source was changed, provider contacted, database migrated, or service started. This report is an assessment, not a production-readiness certification.

**The main distinction is between a valid experiment and a complete trading session.**

A start at 11:00 Eastern cannot prove opening-to-close coverage. It can still prove ingestion, finalization, detectors, publication and stored readers for an explicitly bounded interval. Missing opening tape must remain visible in flow coverage and affected detector outcomes. It should invalidate the full-session claim without making every later experiment impossible. Neither stale input nor missing context should be silently relabeled complete.

Likewise, a checksum does not need to be generated the previous day. Source and image hashes identify software; session hashes identify that day's references, contracts and configuration; per-window hashes identify actual H/E/O evidence. Those have different lifetimes. The current implementation binds these concerns together too tightly.

The next-session restriction comes from the target-promotion policy. [advanced_ingress_repository.py](../backend/realtime/advanced_ingress_repository.py), lines 377–425, requires the child authorization's `valid_from` to equal the exchange session immediately after its parent's `valid_through`. [Migration 023](../backend/realtime/sql_v2/023_realtime_advanced_stream_overlay.sql) also enforces promotion ordering. This is an application policy, not a Massive WebSocket requirement or an inherent hash constraint. The dated October 29 plan identifies the October 28 authorization/promotion failure explicitly. Do not solve this by backdating evidence or disabling checksum validation. Qualify/promote the intended scope once, then generate daily session records under a suitable standing policy.

There is also build/date coupling: [qualify_advanced_options_v3_docker.py](../backend/scripts/qualify_advanced_options_v3_docker.py), lines 237–260, requires an image label containing the target session date as well as the source qualification hash. That prevents ordinary reuse of an unchanged release across dates under this qualification contract. Separate release qualification from daily configuration validation.

**Prioritized implementation findings**

1. **P1 — The scheduled-task launcher cannot invoke the current scheduler successfully.** [register_advanced_realtime_v3_session_task.ps1](../backend/scripts/register_advanced_realtime_v3_session_task.ps1), lines 54–81, constructs a command without `--acquisition-binding` or `--secret-directory`. Both are required by [run_advanced_realtime_session_scheduler.py](../backend/scripts/run_advanced_realtime_session_scheduler.py), lines 392–413. A provider-free parser probe using the wrapper's argument shape exits with code 2 and names both missing arguments. Add parameters, path validation and forwarding, and exercise the wrapper-to-parser contract before another scheduled run.

2. **P1 — Quiet Options acquisition is mistaken for unhealthy acquisition.** [advanced_options_acquisition_runtime.py](../backend/realtime/advanced_options_acquisition_runtime.py), lines 481–497 and 650–669, makes health depend on a status timestamp refreshed by incoming application messages. [advanced_gateway.py](../backend/realtime/advanced_gateway.py), lines 262–273, invokes that update on `recv()`. There is no independent live heartbeat in that path; diagnostic mode has its own heartbeat loop. A status-only probe fails after 31 seconds without a message. An authenticated, subscribed connection can legitimately be quiet before open or for sparse contracts. Use separate process/socket liveness, subscription readiness, last-market-event time and durable-consumer progress. Do not use market activity as the process heartbeat. This is a source-supported live failure scenario, not a claim that this specific failure was observed against Massive in this review.

3. **P1 — A missed window can poison later downstream bindings.** The outer session loop records `FAILED_CYCLE` and continues, which is better than stopping on every cycle failure. But `_attach_downstream_binding` passes `sequence=window.index` at [run_advanced_realtime_session_scheduler.py](../backend/scripts/run_advanced_realtime_session_scheduler.py), line 1064. [P8DownstreamBindingStore](../backend/realtime/advanced_options_p8_runtime.py), lines 724–743, requires the next attached sequence to be exactly the previous sequence plus one. If window 2 fails before attachment, window 3 cannot attach after window 1. A probe with a freshly hashed window-3 binding and the correct previous hash reproduces `P8 downstream binding order changed`. Separate append sequence from market-window index, or retain an explicit terminal record for every scheduled window. Missing data must not block unrelated later windows merely because their ordinal numbers have a gap.

4. **P1 — Binding publication has an unrecoverable interruption interval.** [advanced_options_p8_runtime.py](../backend/realtime/advanced_options_p8_runtime.py), lines 677–769, writes and fsyncs the numbered binding, then writes/replaces `LATEST.json`. Readers require the pointer and full file chain to agree. If the process stops between those operations, `latest()` fails before `attach()` can perform its existing-file replay. An injected failure at `os.replace` followed by retry reproduces `P8 downstream latest binding is unavailable`. Concurrent readers can also observe the intermediate state. Use a database transaction for binding plus pointer, or a file publication protocol where readers consume only committed entries and recovery verifies and reconciles a complete unpointed tail. A leftover `.partial` must be handled explicitly too.

5. **P1 — Coordinator recovery and monitoring do not match unattended operation.** The CLI refuses an existing output directory at [run_advanced_realtime_session_scheduler.py](../backend/scripts/run_advanced_realtime_session_scheduler.py), lines 517–533; `_run` creates fresh state directories and requires services to be absent. Thus lower-level durable stage recovery does not imply coordinator restart recovery. The monitor, lines 2209–2270, turns any sampling exception into `session_stop.set()`. Container inspection, lines 1658–1740, rejects any non-running/non-healthy sample, including a recovery transition. A temporary Docker inspection or database outage can therefore stop otherwise useful acquisition. Add durable coordinator ownership/reconciliation and bounded transient recovery. Keep immediate stop/quarantine for verified identity corruption, unauthorized ownership or unsafe storage failure; distinguish those from telemetry failure and a temporarily unavailable downstream role.

6. **P1 for the alert objective — Canonical stock alerts cannot currently become actionable through the normal context path.** [canonical_stock_alert_product.py](../backend/realtime/canonical_stock_alert_product.py), lines 252–285, always supplies `sector_trend=None` and `event_risk=None`. [feature_engine.py](../backend/equity/model_detection/feature_engine.py), lines 34–40, marks these missing inputs unavailable; [engine.py](../backend/equity/model_detection/engine.py), lines 79–85, returns an unavailable decision. This behavior is honest and documented, but nine persisted evaluations per window do not prove useful stock-alert detection. Implement the context owners, or define and separately validate an explicitly reduced-context model. Do not silently invent context. Keep pipeline completion, model readiness, genuine `NO_MATCH`, and detected matches as separate acceptance measures.

7. **P1 for daily operation — Calendar-derived windows are overridden by a fixed 78-cycle requirement.** [advanced_realtime_session_scheduler.py](../backend/realtime/advanced_realtime_session_scheduler.py), line 267, rejects any authorization with a different count; the executable scheduler, line 3015, repeats the fixed-count success condition. A calendar probe produces 78 windows for October 30 and 42 for November 27, 2026. The latter is a legitimate shortened session, but cannot satisfy this authorization. Derive counts, budgets and success criteria from the calendar and declared run scope throughout preparation, execution, evidence evaluation and qualification.

8. **P1 for daily operation — The existing launcher is a one-session qualification launcher.** [register_advanced_realtime_v3_session_task.ps1](../backend/scripts/register_advanced_realtime_v3_session_task.ps1), lines 156–168, installs a one-time interactive-logon task. It disables catch-up. The Python `--continuous` mode loops through one frozen session and cleans up afterward; it does not prepare tomorrow's references, contract admission, authorities or package. A Docker restart policy does not supply those missing lifecycle responsibilities. Add an exchange-calendar supervisor that remains available across sessions and reconciles after host/daemon restart.

9. **P2 — The live receive path performs synchronous status-file I/O for every WebSocket application message.** The usage callback in [advanced_options_acquisition_runtime.py](../backend/realtime/advanced_options_acquisition_runtime.py), lines 650–669, reads and rewrites status; `_write_json`, lines 371–381, fsyncs and replaces the file. That callback runs inside the gateway's receive coroutine. Although raw journaling is separated into a pump, this status I/O can still delay receipt under high traffic. This is a throughput risk, not a measured capacity failure from this review. Move operational status to a paced writer; preserve conservative durable budget accounting so a crash cannot reset usage. Measure burst arrival rate, durable drain, buffer age, journal latency and session bytes independently.

10. **P2 — Historical readiness remains a real prerequisite and an environment dependency.** [advanced_options_v3_history.py](../backend/realtime/advanced_options_v3_history.py), lines 25–97, pins a historical cohort, manifest and `MASSIVE_DEVELOPER` provider tier. The new live runtime is therefore not yet independently bootstrappable from an arbitrary fresh Advanced database. That does not require running the legacy application, but it does require deliberate baseline provisioning and daily refresh. The retained [October 30 preparation audit](../backend/.realtime-canary/target9-warmup-20261029-for-20261030.json) has verdict `FAIL`: all nine names fail daily/hourly readiness, and its latest coverage is October 28 while `through_session` is October 29. This is historical file evidence, not a fresh database inspection. A count of hundreds of bars is insufficient if the required latest session or lineage is missing. Make the history source configuration explicit and refresh it before each session.

11. **P2 — Source/Docker diagnostics are not yet evidence of live lifecycle correctness.** The current binding split exists: `P8PreopenSessionBinding`, `P8DownstreamBindingStore`, `prepare-waiting`, per-E attachment, and waiting/bound health states are implemented. The dated execution plan's description of that split as absent is stale. However, its passing tests do not cover findings 1–4. The acquisition diagnostic uses a fixed clock and synthetic connection, and the host validation harness seeds disposable fixtures. Retained-provider replay with a real historical baseline is stronger than those structural diagnostics, but still needs a live bounded segment to prove socket behavior and live latency. Maintain distinct evidence for fixture correctness, retained-data replay, Docker lifecycle, live segment, full session and scale.

The acquisition loop also warrants focused stop/reconnect testing: it checks `stop_event` and the authority clock outside an awaited `gateway.run_session`, which itself waits for messages without those stop conditions. A disconnect exception escapes that call, while a quiet open connection may wait through a stop request. Test graceful deadline cancellation, ordinary disconnect/re-authentication, durable usage on restart and gap recovery explicitly before relying on container restarts.

**What should remain in the architecture**

The core flow is appropriate for the current bounded scope:

`concurrent Equity AM and Options T/Q capture -> durable raw journals -> normalization/checkpoints -> Equity E and Options O closure -> independent product evaluation -> immutable projections -> canonical publisher -> stored-only readers`

Keep raw-before-derived durability, immutable H/E/O identities, exact bar/contract lineage, fenced socket ownership, explicit gaps, bounded buffers and provider usage, transactionally coupled database checkpoints, and idempotent publication. Keep optional-lane availability distinct from shared input corruption. An Options failure should not erase Equity evidence. Reader requests should continue to serve stored projections without performing provider or detector work.

Do not rewrite this into a large distributed platform to solve the current target-9/four-contract problems. First prove recovery and capacity at this scope. Broader QQQ/SPY chain capture is a separate workload from four selected contracts, and all-nine Options coverage is a further expansion. The existing broad-stream module is planning/diagnostic infrastructure, not proof that the production four-contract pipeline supports that scope. Massive documents a 1,000-contract quote limit per connection in its [Options quote documentation](https://massive.com/docs/websocket/options/quotes). Actual account entitlements and connection allowances still need to be checked for the intended deployment.

The current E/O scheduler also evaluates on five-minute boundaries with up to 300 seconds between E and O. Real-time WebSocket ingestion does not make this an event-by-event or subsecond alert product. If the intended alert latency is seconds, define a separate event-driven alert lane with its own measured latency budget; portal publication can remain coalesced. The scaling plan's older Developer throughput measurements should not be presented as current Advanced WebSocket benchmarks.

**Suggested validation and deployment sequence**

| Step | Work | Evidence needed |
| --- | --- | --- |
| 1 | Fix launcher, independent heartbeat, skipped-window binding, interrupted binding recovery, and coordinator resume. | Focused regressions reproduce the failures above and pass after repair. |
| 2 | Run the actual stage implementations locally against one disposable PostgreSQL database and sealed provider journals, with an as-of historical/reference baseline. | Bars, lineage, E/O receipts, explicit detector outcomes, publication and readers agree; no fixture is mistaken for real context. |
| 3 | Add fault injection to that replay. | Quiet pre-open, delayed E, one failed cycle followed by successful cycles, interrupted binding commit, coordinator restart, socket disconnect, database interruption and rollback recover as specified. |
| 4 | Run the same artifacts and code in Docker before market hours. | Real roles, persistent volumes, secrets, networking, readiness, restart and stop/drain work; image identity is stable. |
| 5 | Run a bounded live segment, initially 30–60 minutes. | At least three complete consecutive E/O cycles, explicit coverage start, model-readiness outcomes and stored-reader checks; missing opening/long-window evidence remains labeled. |
| 6 | Run a full session in Docker, then several consecutive sessions. | Calendar-derived coverage, opening capture, close drain, overnight preparation, next-session start, retention and restart recovery without daily manual artifact assembly. |

Local-first means host application processes using the production modules and a disposable database; PostgreSQL can itself run in Docker. It does not mean building a second implementation. After deterministic replay passes, Docker should be the routine integration environment because it is the deployment target. A sealed replay permits debugging outside market hours; it cannot establish live network throughput or fresh market latency.

Keep the existing host capture/replay scripts as building blocks, but expose a single supported bounded-segment workflow. It should generate and validate its own session manifests and hashes from declared configuration and actual receipts. Manual copying of dated hashes and report filenames should not be part of normal testing.

**Operating contract needed for unattended Docker**

Use distinct modes with one processing implementation: replay; live non-serving validation; bounded live serving; and daily production. Full-session qualification is an evidence claim, not a prerequisite for every experiment. A durable supervisor should derive exchange clocks, prepare references/history and contracts, start acquisition before the intended coverage boundary, attach each real E, drain at close and prepare the next session. Standalone full-session verdict failure should not automatically revoke useful capture authority.

Use stable release artifacts across days. Bind daily references, selected contracts, budgets and clocks in daily records; bind E/O and publication in window records. Requalify software when software changes. Revalidate daily data and configuration when the session changes. A standing bounded policy can authorize automatic daily preparation without inventing a new manual approval exercise every morning.

Classify failure by scope. Temporary lag retries within the original deadline. A missed window becomes an immutable missed result and later windows continue. Missing lane-specific context affects that lane. Publication failure preserves valid acquisition and prior readable content. Identity corruption, lost ownership or inability to durably capture required evidence requires quarantine or a controlled stop. Network outages require reconnect plus explicit gap/coverage handling; reconnect alone does not restore missed data. Massive's [disconnect guidance](https://massive.com/knowledge-base/article/why-do-massive-websocket-disconnects-happen) confirms that reconnect/re-authentication/resubscription are normal client responsibilities.

Run durable journals and PostgreSQL data on appropriate persistent storage; validate Docker/host path translation and avoid ephemeral container-layer state. Use a persistent supervisor independent of an interactive login. A dedicated always-on Linux host is a reasonable eventual deployment choice, but Windows Docker can validate this scope if host sleep, daemon startup and restart recovery are addressed. Literal uninterrupted market-data availability cannot be guaranteed; the operational target is automatic recovery, visible gaps and correct serving behavior.

Retention is not wholly absent: Compose contains a separate `realtime-v2-retention` service, and the repository has maintenance/archive implementation. Its activation and end-to-end coverage were not verified here. Daily qualification must cover partition creation, safe database retention, journal rotation/archive, disk headroom, backup/restore and metrics without placing maintenance on the capture hot path.

Reconcile the document set around a maintained implementation/acceptance matrix. `REALTIME_V3_PIPELINE.md` is the runtime design reference; the execution checklist should describe current operations; dated runbooks should remain historical evidence. The implementation plan's opening status and later canonical-alert completion section disagree, and the scaling document mixes older baselines with later targets. Clearly distinguish implemented, offline-tested, Docker-tested, live-qualified and continuously operated for every capability.
